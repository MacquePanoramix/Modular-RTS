Reviewer: an agent that did not build them. Question: can a commit or push carry the profile path (<profile>, user name <name>) past the hooks; does a hook refuse what it should not, or hang; can the assistant's commands skip them past G7.

## Must-fix

### M-1. `git replace` hides a dirty blob or commit message from the pre-push check; the push sends the original. CONFIRMED, certain.
Commands (temporary repo): commit a file holding the path with hooks off; `git replace -f <dirty blob> <clean blob>`; `git push origin HEAD:refs/heads/x`. The control push (no replace) is refused. With the replace ref the push passed (rc 0) and the bare remote's blob held the path (read back with cat-file). Same for a commit message (replace the commit by a clean one): pushed, and `git log` on the remote shows the dirty message. Cause: `git rev-list`/`cat-file` in profile_check.py read through refs/replace, while pack-objects sends the real objects. Mend, tested: running the same push with GIT_NO_REPLACE_OBJECTS=1 in the environment made the hook refuse. Close it by putting `--no-replace-objects` (or env GIT_NO_REPLACE_OBJECTS=1) on every git call in profile_check.py (git(), the Popen of cat-file). Closable. (An ordinary user does not run `git replace`; the assistant could. G7 does not mention it.)

### M-2. `git send-pack` pushes without running pre-push. CONFIRMED (file remote), certain.
`git send-pack <bare repo> HEAD:refs/heads/viasend` sent the dirty commit; the control `git push` was refused. G7 passes it (guard cases: `git send-pack ...` rc 0), and G6 in guard.sh passes it too (it only asks the checker for `commit` or `push`). Over https send-pack does not work against GitHub, so for the real remote this is limited to file/ssh remotes, but those are what a second remote could be. Closable in the guard: refuse `git send-pack` (and `git remote-*`, `git http-push`) unless WG_GUARD_OK=G7. Not closable in the hook (git runs no hook there).

### M-3. G7 is bypassed by `git lfs install --force` (replaces the pre-push hook). CONFIRMED, certain.
git-lfs 3.7.1 is installed on this machine. In a temporary repo with our hooks: `git lfs install --local` refuses ("Hook already exists: pre-push", good), but `git lfs install --local --force` overwrote our pre-push (the marker count went from 1 to 0). guard.sh passes `git lfs install --local --force` (rc 0). Closable: refuse `git lfs install` with --force/-f (or any `git lfs install/update` in this repository).
The other direction is a plain should-fix: S-1 below.

### M-4. G7 is bypassed by quoting, variables, and config tricks: the assistant's commands that skip the hooks. CONFIRMED, certain (all run through guard.sh, rc 0 = passed).
Passed (each is a command a shell reads as the refused one):
- skip commit hooks: `git commit --no-ver""ify -m x` (note `--no-verif''y` and `--no-verify""` are refused, so it is the quote join that fails), `git commit "--no-verify" -m x`, `git commit '-n' -m x`, `git "commit" --no-verify -m x`, `"git" commit --no-verify`, `V=--no-verify; git commit $V`, `g=git; $g commit --no-verify`, `git commit $(echo --no-verify)`, (`git commit --no-v -m x` also passes the guard; I did not run it in git, it may be rejected as ambiguous), `git merge --no-verify side` (skips commit-msg and pre-merge-commit; real).
- skip pre-push: `git push "--no-verify" origin main` and `git push --no-ver""ify origin main` pass (both G7 and G6 let them through).
- by alias: `git config alias.ci "commit -n"; git ci -m x`, `git config alias.p "push --no-verify"` then `git p`, `git -c alias.ci=commit ci -n -m x`: G7 sees no `commit` word after git.
- by another config file: `GIT_CONFIG_GLOBAL=/tmp/evil.cfg git commit`, `GIT_CONFIG_SYSTEM=...`, `git -c include.path=/tmp/evil.cfg commit`, `git config include.path ../evil.cfg` (the file, written with the Write tool, holds hooksPath; the command text never says hookspath), `git config -e`, `echo "[core]..." >> .git/config`, `sed -i ... .git/config`.
- spelling hooksPath: `git config core.hooks""Path /tmp/x`, `git config "core.hooks"Path`, `K=core.hooksP; git config ${K}ath /tmp/x`.
- another git directory: `git --git-dir=/tmp/other/.git push`, `GIT_DIR=... git push`, `git clone . /tmp/c2 && cd /tmp/c2 && git push origin HEAD` (a clone has no hooks at all).
- writing into the hooks folder: `cd .git/hooks && printf x > pre-push`, `cd .git && printf x > hooks/pre-push`, `H=.git; printf x > $H/hooks/pre-push`, `printf x > .git/ho""oks/pre-push`, `rm -f .git/./hooks/pre-push`, `rm -f ".git"/hooks/pre-push`, `rm -f .git/hook[s]/pre-push`, `rm -f .git/h*/pre-push`, `cmd /c "del .git\hooks\pre-push"`, `find .git/hooks -type f -delete`, `xargs rm < list`, `dd if=/dev/null of=.git/hooks/pre-push`, `mv .git hooks_gone`, `python -I -c "open('.git/hooks/pre-push','w')..."`.
- the Write and Edit tools: the guard's matcher is Bash|PowerShell, so a file written into .git/hooks (or .git/config) with the Write tool is never seen. I did not run it (the live guard is not mine to test with the tool), but the matcher text in guard.sh's header says exactly this.
Whether it can be closed: the text-matching rule cannot be complete (a shell can always build the word). Cheap partial mends: (a) strip quote marks, backslashes and `${}`/`$x` before matching the flags and hookspath, and refuse any command that has a git word followed by `commit`/`push`/`merge` with a word beginning `-n`/`--no-v` after the quotes are removed; (b) refuse `GIT_CONFIG_GLOBAL|SYSTEM|COUNT|PARAMETERS`, `include.path`, `config -e/--edit`, `alias.` settings that contain commit/push, `GIT_DIR`, `--git-dir`; (c) widen the hooks-folder rule to `.git` + any later `hooks` word and to cd into it; (d) add Write|Edit to the matcher and refuse file_path under .git/hooks or .git/config. The rest (variables, `$(...)`, scripts, python, an unknown tool) belongs on the "cannot see" list, with the true protection being git's own hooks plus the user's review. This is a seat belt against a careless command, not against a determined one; the report should say so.

### M-5. The pre-push check trusts the remote-tracking refs: a made-up one hides a dirty commit. CONFIRMED, certain.
`git update-ref refs/remotes/origin/fake <dirty commit>` then `git push origin <dirty branch>` passed. A less contrived way, also passed: `git fetch <this repo's own path> +refs/heads/dd:refs/remotes/origin/dd2` (a fetch from another folder into origin's namespace), then push. Cause: `rev-list --objects <tip> --not <tracking refs of that remote>`. Cannot be closed without reading the whole history on every push (slow on a large history; I measured 300 commits at about 1 s, but the real history is bigger and the first read of each object costs, see S-2). Recommended: put on the "cannot see" list, with the rule that a tracking ref made by hand or by fetching from elsewhere counts as a way past. Cheap partial mend: also verify that each excluded tracking ref is one `git fetch origin` or a previous push set (not checkable), so no.

## Should-fix

### S-1. The installer refuses outright beside a foreign hook; no chaining. CONFIRMED.
With git lfs hooks in place (`git lfs install --local` wrote post-checkout, post-commit, post-merge, pre-push) install.sh exits 1, changes nothing, and says so (as designed). Result: on a machine with LFS hooks the profile check cannot be installed without the user merging the two by hand. Offer a chain mode (rename the foreign hook to pre-push.foreign and call it at the end), or document the manual merge in install.sh's message. Also: after install, a later `git lfs install --force` removes ours silently (M-3).

### S-2. Hook run on many fresh files takes minutes (looks like a hang). CONFIRMED, measured once per size.
3000 freshly added small files: `git add` 17.7 s, first run of the pre-commit check 49.7 s (about 16 ms per fresh loose object), second run 0.68 s, the commit itself 1.2 s. At 20000 files my first direct run of the check was killed at 100 s with no result and `git add` alone ran over 5 minutes in another attempt; the later runs of the same staged set took 2.4 s. So the first commit of a Unity import (thousands of new files) waits minutes with no output. Not a deadlock as far as I could show; I did not prove the cause beyond the first-open cost the guard's header already names. Mends: print a "profile check: reading N files" line to stderr before it starts; or read the worktree copy when it equals the staged blob (what guard_profile.py does with more than 32 files). A 400 MB clean file: commit 6 s, push 9 s (no hang, no size limit problem).
Also: after a killed run an orphaned `git cat-file --batch --buffer` stayed alive (I found one and ended it). The hook should exit when its stdin is gone; a killed Python cannot do that, so it is only a note.

### S-3. Other spellings of the path that pass the pre-commit check (all CONFIRMED passes; each alone in a temporary repo).
Caught: plain, forward slash, /c/Users, JSON-doubled, upper case, UTF-16LE (with and without BOM, odd offset, upper case), %5C, stored (not deflated) zip, trailing dot, mixed separators, a path across the 16 MB read boundary (UTF-8 and UTF-16), `C--Users-<name>` as a file name, as listed.
Passed: `Users\.\<name>` (a dot segment), `Users_<name>`, `Users <name>` and a newline between `Users\` and the name, `%255C` double encoding, `\u005c` escape, `&#92;` entity, UTF-16BE, UTF-32LE, base64 (aligned or not), gzip, zlib, deflated zip, fullwidth backslash. Innocent controls passed as they should (`%USERPROFILE%`, `C:\Users\Public`, `~/Documents`).
Closable cheaply: allow `\.` segments, `_`, whitespace and newlines in the separator class; add UTF-16BE and UTF-32LE forms. Not closable: base64, any compression (deflate, gzip, Unity packages), anything encrypted. Put those on the "cannot see" list (the docstring already lists UTF-16BE, base64, \u005c and `Users/./<name>`; compression, UTF-32, `_`, whitespace and the double encoding are not named there).

### S-4. G7 refuses innocent commands. CONFIRMED.
- `git config core.hooksPath` (a plain read, no value) is refused; the header says reads pass, but only with --get.
- Reading a hook is refused when its text holds a writer word outside quotes: `grep install .git/hooks/pre-commit`, `grep -n copy ...`, `grep -c move ...`, `grep touch ...` (the words install, copy, move, touch are the verbs). `cp .git/hooks/pre-push /tmp/backup` (copy FROM the hooks) is refused. `ls .git/hooks | tee file` is refused (tee writes a different file). A user making a backup of a hook before a change hits this. Mend: take the verb's first argument position, or allow when the hooks path is only an argument of grep/cat/diff/cmp/ls/head.
These are small; the pass cases checked innocent were all fine: 43 commit/push/config/merge/rebase/tag forms (-s, -S, -e, -uno, --no-edit, --no-gpg-sign, --no-post-rewrite, push -n, --no-verbose, a branch named feature/no-verify-docs) passed.

### S-5. G6 in guard.sh is not asked when git follows `;`, `&&`, `(`, `$(` without a space. CONFIRMED.
With a dirty message and the staged repository as cwd: `git commit -m "<dirty>"` refused, `echo hi; git commit ...` refused, but `echo hi;git commit ...`, `true&&git commit ...`, `(git commit ...)`, `echo $(git commit ...)` passed, as did `git "push" ...` and `x=push; git $x ...`. The hooks still refuse these (git runs them), so this is a second layer failing, not a way past. The pattern G in guard.sh needs `;&|(` and `$(` in the lead-in class (the per-segment code already splits at them, the G6 test uses the whole command). Also G6 only reads when cwd or the payload's cwd is a repository; run from a non-repository cwd every dirty case passed (fails open by design).

### S-6. Fail-open on the hook's own errors. Verified as designed, noted.
With PATH holding git but no python: "profile check skipped: no Python found", commit goes on. With USERPROFILE and HOME both unset (env -u) the dirty commit was still refused (the shell restores HOME), so that case is covered. Whether GitHub Desktop's environment has python on PATH is untested; if it does not, every Desktop commit passes with a warning line the user may never see. Could be closed by looking in the usual places (py launcher, the Python install folder) or by writing the python path into the hook at install time (install.sh knows it).

## Things tried that held (no finding)
Pushes: by remote name, by URL, to a second remote, new branch, `+` force refspec, glob refspec, `--all`, `--mirror`, `--tags`, tag with dirty message on a clean commit, nested annotated tags (inner message dirty), notes ref, refs/stash (with untracked file), from a worktree, remote name with a slash, dry run (`-n`, refused too: the hook runs; harmless). Commits: `--only <path>`, `--amend --no-edit`, empty commit with a dirty `-m`, `-F`, conflicted merge resolved with the path (refused by pre-commit); cherry-pick, rebase, merge --no-ff, revert, commit-tree, fast-import (all refused at push). Content: a mode-120000 entry whose target is the path (refused), a `.gitmodules` with the path (refused), a folder named `C--Users-<name>` (refused on its name), file names with spaces, an apostrophe and a newline (the commit went through without error). Scale: 400 MB clean file, 300 commits pushed by URL, a repository path with a space: no hang, no crash. Installer: run twice (all "unchanged"), foreign hook (refuses, nothing changed, exit 1), from a worktree (writes into the common folder), core.hooksPath set (refuses), uninstall leaves a foreign hook. Hook files are LF.

## Which ways past could be closed
- Closable now: M-1 (one flag), M-2 and M-3 (two guard rules), S-3 (separator class), S-5 (one regex), S-4.
- Partly closable: M-4 (list above).
- Belongs on the "cannot see" list: M-5 (hand-made or fetched tracking refs), compressed and encoded content (S-3), `git clone` elsewhere, a gh api upload, a script or interpreter that runs git, a program that runs no hooks (libgit2, JGit), the Write and Edit tools unless the matcher is widened, variables and substitutions in a command.
