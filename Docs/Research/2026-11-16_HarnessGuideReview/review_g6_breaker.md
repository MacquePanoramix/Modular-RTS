## Held (refused as it should, or passed as it should)
Staged file with the path as backslash, forward slash, MSYS, JSON-escaped (2 and 4 backslashes), upper/lower case, URL-encoded (%5C, %2F), `C--Users-<name>`, `\\?\`, `file:///`, `C:\Users/<name>`, UTF-16LE; names of staged files (also as `C--Users-<name>`); a symlink blob; a gitlink named by the path; `.gitmodules` url; `-m`, `$USERPROFILE`, `$HOME`, `${HOME}`, `$PWD` in a repo under the profile; `M=...; -m "$M"`; `$(cat <<'EOF'` heredoc message; `-F` file; `-C`, `--amend` on an unpushed leaking commit; `--author`, `--trailer`; `git add` of a file that exists, a directory, a quoted glob, `-f`, `-N`, `../f` from a subdirectory, `git -C`; a pathspec commit; `commit -a`; `bash -c`, nested `bash -c`, `cmd /c`, `powershell -Command`; `-C`, `--git-dir`, `cd`; push of the leaking commit, branch, tag (annotated, `tag v1`, `--tags`, `--follow-tags`), notes by name, `--all`, `--mirror`, `-f`, `-u`, `-o`, URL remote, plumbing made on an earlier line; 200 MB staged blob with the path at its end (3.5 s); a 40 MB regex-hostile file (1.9 s); 25 commit segments (2 s). Innocent: name alone, `~`, `%USERPROFILE%`, another user's path, delete pushes, clean pushes, a leak already on origin, a clean tag: all passed.

## Must-fix

**M1. The checker is slow with many objects, so a large ordinary commit or push is refused, or (past 8 s) passes unchecked.**
`ctx.git(['cat-file','--batch-check=%(objectname) %(objecttype) %(objectsize)'], ...)` in `cat()`. On this machine (git 2.51.1.windows.1) that format costs about 2 s plus 7 to 10 ms per loose object; `--batch-check=%(objectsize)` alone, or `--batch`, takes 0.1 to 0.2 s for 1500 objects (measured: 1500 objects, format as written 5.4 to 10 s; `--batch` 0.2 s).
Evidence (staged files, `git commit -m x`, checker alone): 500 files 5.6 s (read, found the path); 1500 files 11.7 s and "too large" refusal (past its own 6 s limit, and past the hook's 10 s); 3000 files 36 s. Through `guard_next.sh`: 3000 files with the path in the last one: exit 0 after 8.3 s, no refusal (`timeout 8` killed the checker, the guard failed open). So a commit of about 700 or more files (this project's largest of the last 300 commits is 160; median 3) is refused as "too large", and of 1500 or more silently passes. A push counts trees and commits too, so five commits of 160 files would be near the limit.
Sure: high (measured, repeated). Closable by the hook: yes, change the cat-file call (read the size with `%(objectsize)` alone, take the type from rev-list/diff, or drop the check and read the `--batch` header).

**M2. A push does not read the path names of the files it sends.**
`check_push` scans the data of blobs, trees, commits, but `where[oid]` (the full path that `rev-list --objects` prints) is only used for the message. A tree holds only one name, so `Users/<name>/x.txt` never shows both parts in one tree object, and a blob's own path is not scanned. Case: a local commit (made earlier) adding `Users/<name>/x.txt` with innocent contents, then `git push` in `cd <repo>`: exit 0, carried to the remote (name found in the remote's file list). The commit check does catch the same name (its `names` list uses full paths), so only the push side misses.
Sure: high. Closable: yes, `has(path)` for each `where` value (and join tree entries with their folder).

**M3. A push that uses a wildcard refspec, or push config, checks the wrong thing or fails open.**
(a) `git push origin 'refs/heads/*:refs/heads/*'`, `'refs/notes/*'`, `'refs/tags/*'`: `rev-list` is given the `*`, git fails, `Failed` is swallowed (the checker's own fail-open), exit 0. Run: carried (heads, notes).
(b) `remote.origin.push = refs/heads/*:refs/heads/*` then `git push origin`, and `push.default=matching` then `git push`: only `HEAD` is checked, other branches go too. Run: carried (a leaking branch other than the current one).
Sure: high for both. Closable: yes. For (a) expand with `git for-each-ref` (or refuse when a refspec has `*`); for (b) read `git config --get-all remote.<r>.push` and `push.default`. A swallowed rev-list failure inside a push should be a refusal, not a pass (it is the only place where "cannot read" passes).

**M4. The checker reads the repository as it is when the command starts; anything the same command does first is unseen.**
All carried, run for real, guard exit 0:
- `echo "<profile>" > f.txt; git add f.txt; git commit -m x`; the same with `sed -i`, with `python -c "open(...).write(...)"` (a generated report holding the path is the likely real leak); `echo ... > m.txt; git commit -F m.txt`.
- `git mv base.txt "Users-<name>.txt" && git commit` (a name), `git stash pop --index && git commit`, `git stash apply --index`, `git apply --index p.diff`, `git update-index --add --cacheinfo ...`, `git checkout o -- f`, `git merge --squash o`, `git cherry-pick -n o`, followed by the commit; `git stash pop && git add f.txt && git commit` (add of a file the pop creates).
- plumbing then push in one line: `hash-object -w`, `update-index`, `write-tree`, `commit-tree`, `update-ref refs/heads/p`, `git push origin p`; `git fast-import <<EOF ... EOF` then push; `git notes add -m "<profile>" && git push origin refs/notes/commits`; `git stash pop --index && git commit && git push`.
Sure: high. Closable by this hook: only in part. The honest list: files written or changed earlier in the line, and any git verb that changes the index before the commit, belong on the checker's "cannot see" list. A real close is a git-native `pre-commit` and `pre-push` hook (the same checker, called by git with the actual index and the actual refs), which sees all of M4, M5-M9 and the scripts of M7; it can be bypassed only by `--no-verify` and by plumbing that never runs a commit hook (a push is still caught by pre-push). Smaller closes in the PreToolUse hook: refuse (as "cannot read") a line that holds a commit or push after a redirect `>` to a file that is then added, or after stash pop/apply, mv, apply, update-index, checkout <rev> --, merge, cherry-pick, notes, fast-import, commit-tree, update-ref.

## Should-fix

**S1. Variables the checker does not follow.** Passed, carried (run): `export M="<profile>"; git commit -m "$M"`, `declare M=...`, `M=$(echo <profile>); ... -m "$M"`. PowerShell, passed: `$env:M = "<profile>"; git commit -m $env:M` (the `env:` branch of `expand()` reads only the environment, not the line's own assignments), `$env:M="<profile>"` and `$m="<profile>"` without spaces around `=`, `git commit -m ($env:USERPROFILE)` and `(Get-Location).Path` (the `(` is read as a separator and ends the `-m` value), here-string piped to `git commit -F -`. Sure: high (not run in PowerShell, since only bash was at hand: verdicts are the checker's, not the shell's). Closable: yes (handle `export`/`declare`/`local`, `$env:X =` with `var`, no-space `=`, parentheses).

**S2. Command substitution and quoting: the git inside is not seen.** Passed, carried: `` echo `git commit ... ` ``, `echo "$(git commit ...)"`, `eval "git commit ..."`, `env bash -c '...'`, `time bash -c '...'` (the wrapper is not in `SHELLS`, and `'git commit ...'` is one word), `bash <<'EOF' ... git commit ... EOF` (the heredoc body is stripped and only searched for the path when the line holds a commit it parsed), 4 levels of nested `sh -c` (depth limit 3), `-m "$(cygpath -w ~)"`, `-m "$(pwd)"`, `-m "$(echo ~)"`, `-m "\`pwd\`"`. For push: the same with `git push`, carried. Windows PowerShell passed: `Start-Process git -ArgumentList "commit",...`, `& "C:\...\git.exe" commit ...` (a quoted path ending in `git.exe` is a word whose base is `git`: the word list then holds `commit` as a word, still passed; I did not trace why), `Invoke-Expression "git commit ..."`, `powershell -EncodedCommand <base64>`. Sure: high that these pass; only `eval`, `env bash -c`, backticks and `"$(...)"` were executed and carried; the PowerShell ones were not run. Closable: wrappers (`env`, `time`, `nohup`, `eval`, `xargs`) and `$(...)`/backticks by recursion; `-EncodedCommand` by decoding (UTF-16LE base64); `$(pwd)`-style by expanding `pwd`, `~`, `$PWD`; scripts a command runs (`bash p.sh`, `./deploy.sh`, `make`) stay on the "cannot see" list (run: a script holding `git push` carried).

**S3. Git aliases and git's own environment.** Passed, carried: `git -c alias.ci=commit ci ...`, a config alias (`git ci`), a shell alias (`!git commit`), `git -c alias.p=push p`, `git ship` (config alias for a push); the trigger regex in `guard_next.sh` needs the word commit or push after git's options, so the checker is not even run. `GIT_DIR=<repo>/.git GIT_WORK_TREE=<repo> git commit` from a clean directory, `export GIT_DIR=...`, `env GIT_DIR=...`: the checker reads the repository of the payload's cwd, not the one the command names (the other repository had the leak staged; guard exit 0; the commit ran there rc=0; I checked by construction, not by reading that other repository). `GIT_INDEX_FILE=<alt>` likewise (carried). `GIT_AUTHOR_NAME="<profile>" git commit` and `-c user.name=...` put the path in the author of the commit (the commit check never reads author/committer; the later push does). Closable: aliases by running the checker on any `git <word>` whose word is an alias (`git config --get-regexp ^alias\.`), env prefixes by passing them to the git calls (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`) and reading `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME`/`-c user.name`.

**S4. The working folder the checker believes in.** `(cd ../other && true); git commit -m x`, `pushd ../other; popd; git commit`, `cd ../other; cd -; git commit`, `cd nonexistent; git commit` (a failed `cd` is skipped, fine) and the push twin `(cd ../o && true); git push origin main`: after a subshell, `popd` and `cd -` the checker's folder stays the last `cd`. Carried (commit and push, run). Closable: yes (scope `( ... )`, handle `popd`, `cd -`).

**S5. `git add` forms.** Passed, carried: `git add {a,b}.txt` (brace expansion), `git add $(ls f.txt)`, `git add $(git ls-files -o --exclude-standard)`, `ls f.txt | xargs git add`; `git add --pathspec-from-file=list` (the file is read relative to the checker's own folder, not the command's: `parse_add` uses `readfile(a.split('=')[1])` without `native(..., ctx.cwd)`, while `check_commit` does). Closable: brace expansion and the relative path, yes; `$(...)` and xargs: cannot see, or refuse when `git add` has a substitution (unreadable).

**S6. A second remote hides a leak.** `rev-list ... --not --remotes` excludes objects that any remote-tracking ref holds. With a private remote `bak` that holds a leaking commit, `git push origin main` passed, carried to origin. The project has one remote today (checked), so low weight. Closable: use `--remotes=<the remote pushed to>` (the first positional, else the branch's, else `remote.pushDefault`, else `origin`).

**S7. Encodings not looked for (passed, not run).** `Users/./<name>`, separators other than `/ \ -` (a space, `_`, `.`), UTF-16BE, UTF-32LE, base64 and hex of the path, `\u005c` escapes, HTML `&#92;`, double-encoded `%255C`, and anything compressed: a zip (deflate), raw zlib. Zip-based formats (docx, xlsx, jar, apk, Unity packages) and `.gz` belong on the "cannot see" list; the rest are unlikely forms. Sure: high that they pass; low that they matter.

**S8. The guard's own bash part hangs on a long command (not G6, but it is in `guard_next.sh`, and the hook's timeout is 10 s).** The same times with the live `guard.sh`: a word of 300 000 characters 11.5 s; 3000 heredocs 13.7 s; 5000 words of the form `"Users/////...."` over 25 s. The checker alone took 0.2 to 0.3 s on all of them, and a regex-hostile 40 MB file 1.7 s, so G6's own code did not hang. Sure: high. Closable: yes, cap the command's length before the regex loops, or fail open when it is over 100 000 characters.

**S9. A refusal of something innocent (minor).** `git commit --allow-empty --template ../m.txt -m x` is refused when the template file holds the path (the template is read as a message although `-m` replaces it in what is stored; checked: git does not store the template text when `-m` is given). Low weight.

## Where each way past belongs
Closable by a hook edit: M1, M2, M3, S1, S3 (aliases, env), S4, S5 (brace, relative path), S6, S8, and in S2 wrappers, backticks, `$(...)`, `-EncodedCommand`.
On the checker's "cannot see" list (or a different layer): files or index changes made earlier in the same command (M4), scripts and `make` (S2), compressed content and exotic encodings (S7), `$(...)` that runs a program.
Best single close for M4, S2 to S5: a git `pre-push` (and `pre-commit`) hook running the same checker, with the PreToolUse rule kept as the early warning; I did not build or test that.
